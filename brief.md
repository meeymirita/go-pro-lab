# Задание на методичку «Go Pro» (часть 2 из 2): Go от среднего уровня до senior

## 0. Как пользоваться этим файлом

Это **готовое задание для генерации методички**. Файл самодостаточный: ничего другого прикладывать не нужно. Исполнитель (ИИ-ассистент) пишет полную лабораторную работу по Go по плану из раздела 3, строго в формате из раздела 2, соблюдая правила из раздела 1.

Если ассистент не умеет выдавать готовый HTML-«бандл», он выдаёт **JSON** со схемой из раздела 2 (поля `units`, `sessions` и т. д.). Из такого JSON методичку собирает владелец проекта. Ссылки на внутренние файлы проекта (`bundle.py` и др.) исполнителю не нужны.

## 1. Кто читает и как писать

- **Читатель:** Laravel/PHP-разработчик, около 1,5 лет опыта. Знает ООП на уровне PHP, HTTP, SQL, Docker на базовом уровне, Git. **Go не видел никогда.** Строго типизированных компилируемых языков не писал.
- **Язык методички: русский.** Термины Go и код — как есть, при первом упоминании термин объяснён по-русски.
- **Главный приём: аналогии с PHP/Laravel.** Для каждого нового понятия коротко «в PHP/Laravel это было бы…» и чем Go отличается (интерфейсы без `implements`, ошибки как значения вместо исключений, структуры вместо классов, горутины вместо очередей/воркеров и т. д.).
- **Метод обучения:** сначала пробуешь сам, потом разбор. Не вываливать длинную теорию заранее. Каждый шаг маленький (15–90 мин), даёт видимый результат (вывод в терминале, тест, ответ сервера).
- **Показывать поведение запуском**, а не словами: специально сломанные примеры, вывод компилятора, `go vet`, `-race`, `pprof`. Каждый шаг заканчивается блоком «ожидаемый результат» (`result`) с реальным выводом.
- **Любое утверждение о коде — проверить запуском до того, как оно попадёт в методичку.** Все команды и весь код выполнить на чистой машине (macOS и Linux), записать реальный вывод. Нельзя придумывать вывод компилятора или версии. Если проверить нельзя, прямо пометить «не проверено запуском».
- **На «сложно» — упрощать**, а не добавлять деталей: аналогия, карта кода, схема. Блоки `deep` («Копнуть глубже») — отдельно и необязательные.
- **Версии-стандарт проекта:** PHP 8.4 (в сравнениях), PostgreSQL 18 (том монтируется в `/var/lib/postgresql`, **не** в `/data`), Redis 8, Docker Compose v2, Kubernetes 1.37 / kind v0.33. **Go: актуальная стабильная версия на день генерации** (проверить на go.dev/dl; ожидается 1.26.x или новее), в `go.mod` указывать её же. Все версии библиотек проверить на pkg.go.dev, закрепить в `go.mod`. Не использовать устаревшее (`ioutil`, `GOPATH`-режим, `interface{}` вместо `any` без причины).
- **Не писать:** пароли, токены, ключи; нерабочие ссылки (каждую ссылку открыть запросом до вставки); пересказ «Зачем» в блоках `deep` (они должны быть новыми по смыслу); эмодзи в теле текста (допустимы только ⚠️ в предупреждениях).
- **Осторожность на машине читателя:** тяжёлые прогоны (бенчмарки на минуты, нагрузочные тесты, сборка больших образов) помечать заранее — ноутбук греется. Docker запускается только когда нужен и описан шаг «как убрать за собой» (`docker compose down -v`, удаление образов).

## 2. Формат результата (схема данных)

Методичка — один объект `window.LAB`. Ключи верхнего уровня:

```
slug        строка, "go-start-lab" или "go-pro-lab"
title       строка, заголовок
subtitle    строка, 1–2 предложения: о чём лаба и что за проект
accent      цвет, например "#00ADD8"
planned     "~48 ч"
introHtml   HTML: вступление «что это, для кого, что получишь»
tocHtml     HTML: оглавление (сессии, разделы)
glossKey    key справочного раздела-глоссария (kind: "ref")
sessions    [{ n, title, dur, steps: ["step-1-1", ...] }]   — «сессия» = блок шагов на одно занятие, 3–7 часов
units       [ ... ]                                           — все разделы и шаги, плоский список
```

Элемент `units` — один из трёх видов (`kind`):

1. **`theory`** — теоретический раздел вне сессий: `{ key: "sec-N", kind: "theory", num, title, short, html, text }`. `html` — готовая разметка, `text` — тот же текст без тегов (для поиска). Поля `html` и `text` **всегда согласованы** (одно и то же содержание).
2. **`step`** — шаг сессии: `{ key: "step-S-N", kind: "step", num: "S.N", title, short, est: "~40 мин", session: "S", intro, result, why, deep, quiz, links, outro, html, text }`.
   - `intro` — что делаем (HTML, с кодом);
   - `result` — ожидаемый реальный вывод (`<pre class="out" data-lang="out"><code>…</code></pre>`) + пояснение, что значит «получилось»;
   - `why` — «Зачем это так»: решение и альтернативы, 3–6 предложений;
   - `deep` — список `{ summary, html }`: необязательные углубления (внутреннее устройство, редкие случаи);
   - `quiz` — 2–4 вопроса **на понимание**, а не на запоминание (строки);
   - `links` — `[{ u: "https://…", n: "что там", t: "название страницы" }]`, только проверенные;
   - `outro` — необязательно, одна фраза-мостик к следующему шагу.
3. **`ref`** — справочный раздел: глоссарий, шпаргалка «Go для PHP-разработчика», «частые ошибки», чек-лист. Формат как у `theory`.

Разметка внутри HTML: обычные `<p>`, `<ul>`, `<ol>`, `<table>`, `<code>`, `<b>`, `<a>`; блоки кода — `<pre data-lang="go"><code>…</code></pre>` (языки: `go`, `bash`, `yaml`, `sql`, `json`, `dockerfile`, `out` для вывода). Код экранировать (`&lt;`, `&amp;`). Каждый блок кода должен быть **полным и запускаемым** или явно помечен как фрагмент.

Требования к полноте:
- каждая сессия: 5–8 шагов; к каждому шагу `why`, `quiz` (≥2 вопросов), `links` (≥2), по возможности `deep` (≥1);
- перед первой сессией — теоретические разделы, которые нужны для сессий 1–3; дальше теория встраивается в `intro` шагов, а не копится отдельно;
- один **сквозной проект** на всю лабу (см. план), каждая сессия наращивает его; в конце каждой сессии проект собирается и проходит тесты;
- ключи (`key`) уникальны, все ключи из `sessions[].steps` существуют в `units`.

## 3. План: «Go от среднего уровня до senior» (часть 2 из 2: «Go Pro»)

**Параметры:** `slug: go-pro-lab`, заголовок «Go Pro: от middle до senior» (репозиторий `meeymirita/go-pro-lab`, папка `go-pro`, файл методички `go-pro.html`), сложность — высокая, `planned ~65 ч`, 13 сессий. Предполагается, что читатель прошёл часть 1 — «Go Start» (`meeymirita/go-start-lab`) или умеет то же: синтаксис, интерфейсы, ошибки, дженерики, базовые горутины и `context`, `net/http`, `database/sql`, тесты, Docker. В начале методички — короткий **входной тест-самопроверка** (10 вопросов); кто не проходит, получает ссылку на нужную сессию «Go Start».

**Цель:** читатель проектирует, пишет, профилирует, защищает, наблюдает и выкатывает в продакшн Go-сервисы; понимает рантайм (планировщик, память, GC); умеет ревьюить чужой код и писать инструменты и расширения; готов к senior-собеседованию и к роли, где отвечает за надёжность и производительность.

**Сквозной проект «CoffeeGo Platform»:** CoffeeGo из «Go Start» превращается в небольшую платформу из трёх сервисов — `orders` (HTTP + gRPC), `payments` (gRPC), `notifications` (потребитель очереди). Данные в PostgreSQL 18, кэш и локи в Redis 8, события через RabbitMQ (по паттерну Outbox, как в RabbitMQ-лабе проекта; Kafka — обзор). Наблюдаемость — OpenTelemetry + Prometheus + Grafana. Развёртывание — kind v0.33 / Kubernetes 1.37. Если читатель не проходил «Go Start», стартовый код `CoffeeGo` выдаётся готовым.

**Структура сессий** (исполнитель раскрывает каждую в 5–8 шагов):

1. **Рантайм изнутри (~4–5 ч).** Планировщик G-M-P (на примере экспериментов, `GOMAXPROCS`, `runtime.Gosched`, `GODEBUG=schedtrace`), стек горутин и рост стека, **escape analysis** (`-gcflags=-m`, что уходит в кучу и почему), аллокатор, **сборщик мусора** (трёхцветная разметка, `GOGC`, `GOMEMLIMIT`, `GODEBUG=gctrace=1`), модель памяти Go (happens-before, что гарантируется, а что нет). Читатель воспроизводит каждое поведение запуском и учится читать вывод, а не заучивать схему.
2. **Профилирование и оптимизация (~5–6 ч).** Бенчмарки как инструмент (`b.Loop`, `-benchmem`, `benchstat`), `pprof` (CPU, heap, allocs, goroutine, mutex, block), flame graph, `go tool trace`, `runtime/metrics`, PGO (profile-guided optimization), типовые узкие места (лишние аллокации, `fmt` в горячем пути, преобразования строк, блокировки, JSON), `sync.Pool`, предвыделение срезов и карт, структурное выравнивание. Правило: сначала измерить, потом менять; каждое улучшение — с цифрами «до/после». Тяжёлые прогоны помечать. Стенд: горячая ручка `orders` из CoffeeGo.
3. **Конкурентность II (~6 ч).** Паттерны: pipeline, fan-out/fan-in, bounded parallelism (семафор на `chan` или `x/sync/semaphore`), `errgroup` с лимитом, `singleflight`, rate limiter (`x/time/rate`), pub/sub в процессе, `sync.Once*`, `sync.Cond`, `atomic.Value`/`atomic.Pointer`, lock-free vs mutex (когда что), отмена и дедлайны сквозь весь стек, **утечки горутин** (поиск через `pprof` и `goleak`), тестирование конкурентного кода (`-race`, `testing/synctest`), типовые дедлоки и как их читать из дампа горутин.
4. **Продвинутые типы и язык (~5 ч).** Дженерики глубже (ограничения, наборы типов, когда сложность не окупается, ограничения реализации), итераторы (`iter.Seq`, range-over-func, `iter.Pull`), `reflect` (когда необходимо, цена), struct-теги и свой мини-валидатор, embedding и его подводные камни, `unique`, `weak`, `slices`/`maps` продвинуто, `encoding/json/v2` (текущий статус и отличия — проверить на день генерации), `errors` на уровне дизайна (дерево ошибок, `Join`, контекст ошибки), `any`-антипаттерны.
5. **Дизайн кода и архитектура (~5 ч).** Дизайн пакетов и API (мало экспортируемого, имена, зависимости, стабильность), интерфейсы на стороне потребителя, functional options, конструкторы, внедрение зависимостей руками vs `wire`/`fx` (когда что), слои (hexagonal/clean без церемоний), доменные ошибки и границы транзакций, **когда Go-проект стоит делить на модули/сервисы**, версионирование API, обратная совместимость и deprecation. Рефакторинг «плохого» кода CoffeeGo: читатель получает намеренно неудачный кусок и приводит его в порядок с обоснованием каждого решения. Ревью по Go Code Review Comments и Uber Go Style Guide.
6. **Сервисы: HTTP, OpenAPI, gRPC (~6 ч).** Продвинутый `net/http` (таймауты всех видов, `http.Server` настройка, `Transport`, `HTTP/2`, потоковая передача, SSE), роутеры (`chi` vs стандартный `ServeMux` — когда что), **contract-first**: OpenAPI + кодогенерация (`oapi-codegen`), gRPC и Protocol Buffers (`buf`, потоковые вызовы, статус-коды, deadline, метаданные, interceptors), `connect-go` (обзор), версионирование схем, обратная совместимость protobuf, gRPC-Gateway (обзор). Реализация `payments` как gRPC-сервиса и вызов из `orders`.
7. **Данные: PostgreSQL, Redis, очереди (~7 ч).** `pgx` и пул (настройка, тайм-ауты, мониторинг), транзакции и уровни изоляции, ретраи при сериализационных ошибках, **Outbox** и идемпотентность, `sqlc`, миграции в продакшне (совместимость при rolling deploy), `EXPLAIN` из Go-кода, `go-redis` (кэш, локи, rate limit, Streams), RabbitMQ-потребитель (подтверждения, повторы, DLQ, идемпотентный обработчик), Kafka — обзор. Ссылки на соответствующие лабы проекта (PostgreSQL, Redis, RabbitMQ). Тесты на реальных зависимостях через `testcontainers-go`.
8. **Наблюдаемость (~5 ч).** `log/slog` (структурные логи, корреляция), OpenTelemetry (трассы между сервисами, метрики, контекст-пропагация через HTTP, gRPC и очередь), Prometheus и Grafana в Compose, RED/USE-метрики, SLI/SLO и алерты (на уровне идеи и одного примера), `/healthz`/`/readyz`, `expvar`/`runtime/metrics`, continuous profiling (обзор). Результат: одна трасса заказа проходит через все три сервиса и видна в UI.
9. **Надёжность (~5–6 ч).** Таймауты и дедлайны через границы сервисов, ретраи с экспоненциальной задержкой и джиттером, идемпотентность запросов, circuit breaker, bulkhead, backpressure, graceful shutdown (все компоненты в правильном порядке), degraded mode, управление нагрузкой (`x/time/rate`, очередь с лимитом), **хаос-упражнения**: убить БД, замедлить сеть, перегрузить сервис, и наблюдать. k6 или `vegeta` для нагрузки; тяжёлые прогоны помечать. Результат: документ «что ломается и как мы это увидели».
10. **Безопасность (~5 ч).** Валидация и границы доверия, аутентификация (JWT, OIDC, сессии; библиотеки, а не самописное), авторизация (RBAC/ABAC на примере), стандартная криптография (`crypto/*`, что нельзя изобретать), хеширование паролей (`argon2id`/`bcrypt`), TLS и mTLS между сервисами, секреты, `govulncheck`, `gosec`, цепочка поставок (`go.sum`, `GOFLAGS=-mod=readonly`, `GOPROXY`, проверка зависимостей, SBOM), SSRF/инъекции/гонки как класс уязвимостей в Go, fuzzing для безопасности.
11. **Тестирование на уровне senior (~5 ч).** Пирамида тестов в Go-проекте, интеграционные тесты (`testcontainers-go`), контрактные тесты (gRPC/OpenAPI), property-based (`rapid`), fuzzing, golden-файлы, фейки vs моки (когда `gomock`/`mockery` оправданы), детерминированное время, `testing/synctest`, тесты на гонки, бенчмарки в CI с `benchstat`, стабильность тестов (flaky), покрытие как метрика с оговорками, мутационное тестирование (обзор).
12. **Инструменты, кодогенерация, расширения (~6 ч).** `go generate`, `text/template`, `go/ast`, `go/parser`, `go/types`, **свой анализатор** на `golang.org/x/tools/go/analysis` (линтер, который ловит реальную ошибку в проекте), build tags, `embed`, `unsafe` (когда нужен, как не стрелять в ногу), `cgo` (основы, цена), WebAssembly (`GOOS=wasip1`, TinyGo — обзор), плагины и расширяемость (в т. ч. **свой модуль для Caddy** — связь с Caddy Lab проекта), самодельная CLI-утилита на `cobra`, выпуск через `goreleaser`.
13. **Продакшн и итог: Kubernetes, CI/CD, приёмка (~6–7 ч).** Минимальные образы (distroless, `ko`), деплой трёх сервисов на kind v0.33 / Kubernetes 1.37 (Deployment, Service, ConfigMap, Secret, probes, HPA — ссылка на Kubernetes-лабу проекта), `GOMEMLIMIT` и лимиты контейнера (ловушка: OOMKill), `GOMAXPROCS` в контейнере (что изменилось в свежих версиях — проверить), rolling update без потери запросов, CI/CD (GitHub Actions: тесты, линтеры, `govulncheck`, образы, подпись), семантическое версионирование модулей (`v2+`), монорепо и `go work`, ADR (architecture decision records), **чек-лист senior**: что проверять в ревью, перед релизом, при инциденте; разбор постмортема на примере проекта; вопросы senior-собеседования с разбором (рантайм, память, конкурентность, дизайн, надёжность).

**Теоретические разделы:** «Что такое senior в Go» (ответственность, границы, ревью, принятие решений), «Как читать рантайм и инструменты», «Дерево решений: когда что выбирать» (мьютекс или канал, ORM или `sqlc`, один сервис или несколько, дженерик или интерфейс), «Карта изученного».

**Справочные разделы (`ref`):** глоссарий; «флаги и переменные окружения Go-рантайма» (`GODEBUG`, `GOGC`, `GOMEMLIMIT`, `GOMAXPROCS`, `GOFLAGS`); «команды `go tool`» (pprof, trace, cover, vet, nm, objdump); шпаргалка по `pprof`; чек-лист ревью; чек-лист релиза; чек-лист инцидента; «20 разборов реальных ошибок» (утечка горутин, гонка, deadlock, OOMKill, лавина ретраев, `Body` не закрыт, неверный `context`, гонка в кэше — с кодом, причиной и починкой).

**Особые требования к этой методичке:**
- Все утверждения про рантайм подтверждены экспериментом из шага: вывод `gctrace`, `schedtrace`, `pprof` — реальный, с версией Go, на которой снят. Если поведение зависит от версии, это указано.
- Нагрузочные эксперименты предупреждают о нагрузке на ноутбук, имеют лимит времени и инструкцию «остановить и убрать».
- Ссылки на лабы проекта (PostgreSQL, Redis, RabbitMQ, Kubernetes, Caddy) даются как «если не проходил — достаточно прочитать раздел N», сама методичка самодостаточна.
- Последняя сессия содержит **самостоятельный финальный проект без подсказок** (описание требований и критериев приёмки, без пошагового решения): добавить в платформу новый сервис или возможность и пройти по чек-листу senior.

## 4. Дополнительные материалы, которые нужно выдать вместе с методичкой

1. **Код сквозного проекта** — по сессиям (ветка или папка `session-N/` с итоговым состоянием после каждой сессии), чтобы читатель мог сверить своё решение. Весь код проверен: `go build ./...`, `go vet ./...`, `go test -race ./...` проходят.
2. **README лабы:** название, сложность, время, что получишь, предварительные знания, установка, строка «**Статус:** …» (что проверено запуском, что нет), структура сессий, ссылка на методичку, лицензия (код — MIT, тексты — CC BY 4.0).
3. **Список проверок:** какие команды и на какой ОС/версии Go реально запускались, что не удалось проверить.
4. **Список источников** (официальные: go.dev, pkg.go.dev, Go blog, Effective Go, Go Code Review Comments, Uber Go Style Guide, документация библиотек) с датой проверки.

## 5. Приёмка (исполнитель проверяет себя перед сдачей)

- Нет ни одного блока кода, который не запускался.
- Нет выдуманного вывода команд.
- Все ссылки открываются.
